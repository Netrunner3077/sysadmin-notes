Скриптинг и автоматизация

Как перестать делать одно и то же руками: bash, PowerShell, cron, Ansible и CI/CD. Глава 8 учебного курса.

Зачем автоматизировать

Хороший администратор — ленивый администратор. Не в смысле «ничего не делает«, а в смысле «не делает дважды одно и то же«. Если вы в третий раз вводите одну и ту же последовательность команд — пора писать скрипт.

Экономия времени

Настройка 50 серверов вручную займёт день. Скрипт справится за 5 минут.

Меньше ошибок

Человек устаёт и ошибается. Скрипт делает одно и то же одинаково хорошо в любое время суток.

Документация сама собой

Скрипт — это ещё и описание того, что именно было сделано на сервере.

«Автоматизируй всё, что делаешь больше двух раз. Исключение — если задача требует творчества.«

Bash: скрипты для Linux

Bash — стандартная оболочка почти всех Linux-систем. Если вы освоили командную строку, следующий шаг — научиться складывать команды в сценарии.

Структура скрипта

#!/bin/bash
# Первая строка — «шебанг«, указывает интерпретатор

# Переменные
NAME="admin"
DATE=$(date +%F)

# Условие
if [ -d "/var/log" ]; then
    echo "Каталог логов найден"
else
    echo "Каталог отсутствует"
fi

# Цикл
for file in /etc/*.conf; do
    echo "Найден конфиг: $file"
done

# Функция
greet() {
    echo "Привет, $1!"
}
greet "$NAME"

Основные конструкции

  • 1 Переменные: VAR="value", $VAR
  • 2 Условия: if / elif / else
  • 3 Циклы: for, while, until
  • 4 Функции: name() { ... }
  • 5 Пайпы: cmd1 | cmd2
  • 6 Перенаправления: >, >>, 2>&1

Совет: проверяйте скрипты через shellcheck. Он найдёт 90% типичных ошибок ещё до запуска: незакрытые кавычки, необъявленные переменные, неверные условия.

PowerShell: скрипты для Windows

PowerShell — современная оболочка Windows. В отличие от старого cmd, она работает с объектами, а не с текстом. Это делает её гораздо мощнее для администрирования.

Пример скрипта

# Переменные
$Name = "Admin"
$Date = Get-Date -Format "yyyy-MM-dd"

# Условие
if (Test-Path "C:\Logs") {
    Write-Host "Каталог логов найден"
} else {
    New-Item -Path "C:\Logs" -ItemType Directory
}

# Цикл по файлам
Get-ChildItem "C:\Configs\*.xml" | ForEach-Object {
    Write-Host "Найден конфиг: $($_.Name)"
}

# Функция
function Greet {
    param([string]$UserName)
    Write-Host "Привет, $UserName!"
}
Greet -UserName $Name

Почему PowerShell, а не cmd

Объекты вместо текста

Команды возвращают не строки, а объекты с полями. Не нужно «парсить« вывод — можно сразу обратиться к нужному свойству.

Единый синтаксис

Все команды построены по схеме «глагол-существительное«: Get-Service, Stop-Service, New-Item.

Интеграция с .NET

Можно вызывать любые библиотеки .NET напрямую. Это делает PowerShell почти полноценным языком.

Сравнение синтаксиса

Задача Bash PowerShell
Переменная VAR="value" $Var = "value"
Условие if [ -f file ] if (Test-Path file)
Цикл for f in *.txt Get-ChildItem *.txt | ForEach-Object
Вывод echo "text" Write-Host "text"
Файл скрипта script.sh script.ps1

Планировщики задач

Не все скрипты запускаются вручную. Большинство работает по расписанию: бэкапы ночью, обновления в выходные, проверки каждые пять минут.

cron в Linux

cron — демон, запускающий команды по расписанию. Расписание описывается в формате из пяти полей: 

# ┌── минута (0-59)
# │ ┌── час (0-23)
# │ │ ┌── день месяца (1-31)
# │ │ │ ┌── месяц (1-12)
# │ │ │ │ ┌── день недели (0-7, 0 и 7 = воскресенье)
# │ │ │ │ │
# * * * * * command

# Каждый день в 3:30 утра — бэкап
30 3 * * * /usr/local/bin/backup.sh

# Каждые 5 минут — проверка состояния сервиса
*/5 * * * * /usr/local/bin/check-service.sh

# По понедельникам в 9:00 — отчёт
0 9 * * 1 /usr/local/bin/weekly-report.sh

# Редактировать расписание
crontab -e

# Посмотреть текущие задачи
crontab -l

Task Scheduler в Windows

Аналог cron, но с графическим интерфейсом. Создаётся через taskschd.msc или командой schtasks. 

# Создать задачу через CLI
schtasks /create /tn "DailyBackup" ^
    /tr "C:\Scripts\backup.ps1" ^
    /sc daily /st 03:30

# Запустить вручную
schtasks /run /tn "DailyBackup"

# Удалить
schtasks /delete /tn "DailyBackup" /f

Совет: запускайте тяжёлые задачи ночью. Днём сервер загружен пользователями, и бэкап может испортить всем жизнь. Также следите за пересечением расписаний — два тяжёлых скрипта в 3:00 одновременно положат диск.

Ansible: управление конфигурациями

Когда у вас 5 серверов, bash-скрипт справится. Когда 500 — нужен инструмент, который опишет желаемое состояние всех машин сразу. Ansible — самый популярный open-source вариант.

Ключевые идеи

  • 1 Работает по SSH — ничего не нужно ставить на целевые машины
  • 2 Конфигурации описываются в YAML — читаемо и понятно
  • 3 Идемпотентность — повторный запуск не ломает систему
  • 4 Есть готовые модули почти под любую задачу
  • 5 Не требует центрального агента — работает «из коробки«

Пример playbook

---
- name: Настройка веб-сервера
  hosts: webservers
  become: yes

  tasks:
    - name: Установить nginx
      apt:
        name: nginx
        state: present

    - name: Скопировать конфигурацию
      copy:
        src: files/nginx.conf
        dest: /etc/nginx/nginx.conf
      notify: Перезапустить nginx

    - name: Запустить сервис
      service:
        name: nginx
        state: started
        enabled: yes

  handlers:
    - name: Перезапустить nginx
      service:
        name: nginx
        state: restarted

Один такой файл — и вы готовы развернуть веб-сервер на сотне машин одной командой: ansible-playbook site.yml.

Аналоги Ansible

Puppet

Мощный, но требует агента на каждой машине. Популярен в крупных корпорациях.

Chef

Гибкий, программируемый на Ruby. Крутая кривая обучения.

SaltStack

Очень быстрый, работает через ZeroMQ. Подходит для тысяч машин.

CI/CD: автоматизация поставки

CI/CD — это про автоматизацию всего пути кода от разработчика до продакшена. Ручной деплой — источник ошибок и ночных звонков.

Что означают аббревиатуры

  • CI Continuous Integration — автоматическая сборка и тесты при каждом коммите
  • CD Continuous Delivery — код всегда готов к выкатке в прод
  • CD Continuous Deployment — выкатка в прод без ручного подтверждения

Типичный пайплайн

  1. Разработчик пушит код в репозиторий.
  2. CI-система собирает приложение и запускает тесты.
  3. При успехе собирается Docker-образ и публикуется в реестр.
  4. CD-система разворачивает образ в тестовой среде.
  5. Проходит приёмочное тестирование и security-скан.
  6. Автоматически или по кнопке выкатывается в продакшен.

Инструменты

GitLab CI

Встроен в GitLab. Конфигурация в .gitlab-ci.yml. Можно поднять self-hosted.

GitHub Actions

Бесплатно для open-source. Огромная библиотека готовых действий.

Jenkins

Ветеран индустрии. Гибкий, но требует времени на настройку и поддержку.

Лучшие практики

Автоматизация без дисциплины может навредить: один плохой скрипт положит всю инфраструктуру быстрее, чем ручная ошибка. Вот что стоит помнить.

  • Храните скрипты в Git. Не на рабочем столе, не в блокноте — в репозитории с историей изменений.
  • Пишите комментарии. Через полгода вы не вспомните, зачем в скрипте «вот эта странная проверка«.
  • Обрабатывайте ошибки. set -e в bash остановит скрипт при первой ошибке. Без него скрипт продолжит работу, нанося ущерб.
  • Логируйте всё. Куда писать, с какой детализацией, что делать при ошибке — должно быть решено заранее.
  • Тестируйте на копии. Сначала в dev-среде, потом в проде. Никаких исключений.
  • Не автоматизируйте хаос. Сначала наведите порядок в процессах вручную, потом автоматизируйте.
  • Идемпотентность. Повторный запуск скрипта не должен ничего ломать.
«Автоматизация — это не про экономию времени сегодня. Это про то, чтобы завтра не пришлось делать это снова.«

Практический совет

Начните с малого. Не пытайтесь сразу написать идеальную систему управления конфигурациями. Возьмите одну рутинную задачу — например, ротацию логов — и напишите для неё скрипт. Потом повесьте его на cron. Через месяц добавите второй. Через год у вас будет своя автоматизированная инфраструктура.

Совет: учитесь читать чужие скрипты. GitHub полон готовых решений. Прежде чем писать своё, поищите — возможно, кто-то уже решил эту задачу лучше.
